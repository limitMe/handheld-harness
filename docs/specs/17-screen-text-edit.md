# 17 · 界面：文本编辑

> 阶段 B · 方向性 spec。

## 目标

提供一个专门为"语音输入后的精修"设计的叠层界面：用大字号逐句显示文本，用手柄选中句子、删除句子，再用语音补充，尽量不用键盘。

## 依赖

- 11、12、16。

## 设计方向

### 进入和退出

- **进入**：输入框激活时按 RB（产品文档写的是"在某些位置按下特定键"，目前只确定了输入框这一个入口）。把输入框的当前文本带进来。
- **退出**（P-07）：按 B 退出，**默认确认修改**：把编辑后的文本写回输入框，并恢复输入框的激活状态。没有"放弃修改"的操作；删错了靠撤销（P-17）。

### 布局

- 状态栏**没有标题**。
- 以叠层的形式出现：背景是原来的界面，加模糊（性能不够时退化为半透明遮罩，见 18）。这样用户能看出当前编辑是基于原来那个界面的。
- 中间偏下放一个**麦克风图标**。长按 Y 时显示为激活状态，可以带电平动画。
- 麦克风上方是若干行**大字号**文本。
- 文本下方**留出空白**。极端情况下，用户可以呼出系统触屏键盘直接输入，键盘不会挡住文本。

### 句子模型

- 分句规则：
  - 按中文的 `。！？；` 和英文的 `. ! ? ;`（后面跟空格或位于结尾）切分；
  - 换行一定切分；
  - 引号、括号、代码片段（反引号包住的部分）内部不切分。
- 每个句子都是一个 `Focusable`（11）。
  - 左 / 右：在前后句子之间移动；
  - 上 / 下：按屏幕上的行移动，可以用 `geometric` 方式。
- 句子聚焦后等待一会儿，显示操作提示（12），例如 X 删除整句。
- 按 X 删除聚焦的句子，焦点移到下一句；如果删的是最后一句，就移到上一句。这个操作需要支持撤销（P-17：撤销用哪个键）。

### 听写

- 长按 Y：**插入到聚焦句子之后**（P-07）。因为有专门的按键（X）删除聚焦的句子，所以听写不需要"替换"的模式。
- 听写的协议和临时文本显示复用 16。在服务商选定之前（P-06），这里只能用 Mock 测试；句子的选择和删除不依赖语音，可以先做。
- **聚焦句子的视觉**：除了被选中的高亮外，在句子末尾显示一个**闪烁的光标**，表示新的语音内容会接在这里。听写过程中，临时文本接在光标处出现。

### 触屏键盘兜底

- 可以选择一个句子进入"键盘编辑"：把它放进一个原生输入框，让系统弹出触屏键盘。
- Windows 上用代码主动弹出触屏键盘并不可靠，需要调研。在平板模式下，原生输入框获得焦点时一般会自动弹出键盘。

## 验收方向

- 只用手柄完成：语音输入一段三句话 → 按 RB 进入文本编辑 → 删除第二句 → 长按 Y 补充一句（需要 16 选定服务商之后；之前用 Mock 验证）→ B 退出，回到输入框后文本正确 → 发送。
- 聚焦的句子末尾有闪烁光标；听写的内容接在聚焦句子之后。
- 中英混合文本的分句结果符合预期（单元测试）。

## 待定输入

- 渲染层新增 `src/renderer/src/textedit/`：

  - `store.ts`：`open` / `source` / `caret` / `revision`，用于输入框、叠层与状态栏之间协调。
  - `TextEdit.tsx`：叠层界面（`text-edit-scope` 模态作用域）。句子**按原文内联排版**，只保留原始分隔与换行；聚焦句用高亮表示、句末有闪烁光标；麦克风图标在文本下方，听写时按电平点亮。

  - `Composer` 在激活状态下按 RB 打开（带入当前草稿与光标位置）；关闭时把编辑结果写回草稿并恢复输入框的激活状态。
  - 听写复用 16：文本编辑期间注册自己的 `DictationTarget`（整段文本 + 聚焦句末光标），长按 Y 的结果插入到聚焦句之后。
  - `StatusBar` 在编辑界面打开时不显示标题。
  - `DictationController.registerTarget` 增加 owner：输入框在叠层打开时注销自己的 target 不会误清掉文本编辑注册的 target。

### 与正文的出入 / 已决定（P-17）

- **导航**：正文写"左右在句子间移动、上下按行移动"；实现为**统一的几何导航**——四个方向都取最接近的句子，十字键与两摇杆都可移动（用户反馈）。

### 后续补充（2026-10-08）：B 文案与屏幕键盘

- **B 的"保存并返回"提示**：B 原来绑定 `nav.deactivate`，被操作提示层（12）作为"返回"隐藏，界面上看不到。新增语义动作 `edit.commit`（en `Save & return` / zh `保存并返回`），B 改绑它；`TextEdit` 同时为它和键盘的 `nav.deactivate`（Esc）注册同一个退出回调。
- **RB 呼出屏幕键盘**：新增语义动作 `keyboard.show`（en `On-screen keyboard` / zh `屏幕键盘`），`textEdit` 上下文把 RB 绑到它。渲染层通过新 IPC `app:showOnScreenKeyboard` 调用主进程 `src/main/on-screen-keyboard.ts`。
- **隐藏输入框（第二轮）**：文本编辑页是只读排版，没有可编辑控件，触屏键盘没有输入宿主，所以按下 RB 什么都不会发生。页面上加一个视觉不可见但可聚焦的 `<textarea>`（`data-testid="text-edit-keyboard"`），呼出键盘时定位到聚焦句末的闪烁光标处（便于 IME 候选窗跟随）并聚焦；它的输入实时插入到当前 selection 并前进光标，`Backspace` 在光标处向前删一个字符，输入框自身始终清空。这样物理键盘和在屏幕键盘上敲入的字符都能落到真正的文本上，光标位置保留。在单句原生编辑态（A）下不再用隐藏框——那个 textarea 本身已经是输入宿主。
- **Windows 调研结论（第二轮）**：桌面（Win32）应用**没有**弹出触屏键盘的正式 API（WinRT 的 `InputPane` 只对 UWP 有效，`ITextInputPanel` 已废弃）。实测：现代触屏键盘 `TabTip.exe` 在触屏设备上是**常驻单实例**进程（本机 PID 31028，窗口全隐藏），spawn 无法显示它；未公开的 COM `ITipInvocation::Toggle`（Win10/Win11 CLSID 不同）在本机调用不报错但不产生可见键盘，聚焦可编辑控件也不稳定。经典 `osk.exe` 实测稳定弹出（普通顶层窗口、单实例、可正常关闭）。
- **第三轮（用户实测反馈）**：用户设备上聚焦输入框会**自动弹出现代触屏键盘**，进入文本编辑页时在 OSK 之前它就已经出现——这正是正文第 49 行预判的行为：Chromium/Electron 自带的 input-pane 集成会在可编辑控件获得焦点时拉起系统触屏键盘，不需要应用调用任何 API，也不需要模拟触控事件（合成 DOM 事件操作系统看不到）。所以隐藏输入框 `focus()` 本身就是"呼出"。`osk.exe` 只在 `navigator.maxTouchPoints === 0`（无触屏）的设备上作为兜底，避免在现代键盘之上再叠一层经典键盘。另外打开文本编辑页时把 Composer 的 textarea `blur()`，让键盘锚定到编辑页的隐藏框而不是背后仍在激活的输入框。
- 键盘呼出逻辑抽成带依赖注入的纯函数（`src/main/on-screen-keyboard.ts`）；`ipc-contract`、`hint-entries`、`textedit` 单测同步更新。

### 后续补充（2026-10-08）：按住 X 连续删除

- **X 支持按住重复**（用户 2026-10-08 决定）：文本输入框里按住 X 不再只删一个字符，而是按 input 系统既有的重复节拍（350 ms 后每 60 ms）持续向前删除，和物理键盘的自动重复一致。实现只需把 `input.deleteBackward` 标记为 `repeatable`（`src/shared/actions.ts`）；`GestureResolver` 已具备重复能力，各输入框的 `onPress` 处理器（`Composer`、`TextEdit`、`ModelsPage` 搜索框）也已经在 `repeat` 相位触发。键盘路径本就有 OS 自动重复，不受影响。
